**Track declared: B (Offer Generation — RAG)**

## 1. Churn model: why gradient boosting

This dataset is ~10,000 customers with 11 engineered features feeding a binary label, and the retention team needs to know *why* a given customer was flagged. A neural network buys nothing here. With only 11 features and ~7,000 training rows, there isn't enough data for a network to find anything a shallow tree ensemble can't. This was measured directly using three XGBoost configurations: depth 4/eta 0.2/100 rounds, depth 6/eta 0.1/200 rounds, depth 8/eta 0.05/400 rounds. Which produced AUC 0.7729, 0.7773, and 0.7808. This only changed the AUC by 0.008. A model with far more capacity than that would be fitting noise, not finding structure, and would hand the retention team a black box in exchange for nothing.

Logistic regression was the real alternative, it's at least as interpretable as a shallow tree ensemble via coefficients, and on 11 clean numeric features it's a fair fight. I chose XGBoost over it because the churn signal is not expected to be linear — `category_diversity_score` and `online_to_store_ratio` plausibly interact with recency rather than contributing independent additive effects (a customer who still buys frequently but only in one category is a different risk profile than one who buys broadly but rarely), and a tree ensemble captures that interaction without us hand-specifying it. Feature importance plots and SHAP-style single-tree inspection still give the retention team a defensible "why" per prediction, which a hidden-layer network would not.

What would change our mind: if the retention team's actual complaint became "the model's reasoning is opaque" rather than "the model isn't accurate enough," then the move to logistic regression specifically for its transparent coefficients, accepting the small accuracy cost measured above.

## 2. What the features bought

The full model's AUC (0.7773) beat the recency-only baseline (`days_since_last_purchase` alone, AUC 0.7232) by +0.0541, with a bootstrapped 95% CI of [0.0344, 0.0737] that excludes zero. That modesty is explained by the slice evaluation: Platinum customers have the *highest* per-tier AUC (0.8631) of any tier, meaning the model separates Platinum churners from non-churners better than any other segment, yet Platinum's recal at 10% is the *lowest* (0.095) because a flat top-10%-of-everyone contact budget systematically underweights a tier whose absolute risk scores run lower even when correctly ranked internally. The behavioral features (`category_diversity_score`, `online_to_store_ratio`, basket size) are what let the model catch the roughly one-third of churners who still look recency-healthy; `churn_risk_score` itself was deliberately excluded as an input precisely because it's the thing we're trying to beat, not a feature to lean on.

## 3. RAG over fine-tuning, and its main risk

Fine-tuning a model on example offers would require hundreds of labeled "good offer" examples per tier/category combination that don't exist yet, and would still need to be retrained every time a policy number changes (free-shipping threshold, return window). RAG decouples policy facts from the generation model entirely — correcting a threshold means editing a markdown file, not retraining. The primary production risk is **fabricated promotional specifics**: across five sampled generations, two invented a concrete numeric incentive ("10 bonus points," "25% extra points") that appears nowhere in the retrieved context or the static tier-benefits text, despite an explicit system-prompt instruction not to. A live test additionally produced a Gold customer offered 48-hour early access — a real benefit, just the wrong tier's. Prompt instructions alone did not prevent either failure mode; a production system would need a deterministic post-generation check (extract every number/benefit claim, verify it appears in retrieved context or matches the customer's actual tier row) before anything reaches a customer, because an offer promising a benefit NorthStar won't honor generates a support cost larger than the churn it was meant to prevent.

## 4. With 10× the time or data

For the churn model: a larger Feature Group would shrink the Platinum slice's uncertainty (currently n=307, 21 positives — usable but the thinnest of the four tiers) and support a proper nested cross-validation sweep instead of three hand-picked configurations. For Track B: the biggest change would be the post-generation fact-checker described above, shipped as code rather than documented as a known gap, plus a larger policy corpus, the three retrieval query strategies converge on nearly identical retrieved content regardless of customer tier or channel, so more corpus and genuinely differentiated per-customer policy detail would be needed before retrieval strategy choice meaningfully changes what gets generated.
